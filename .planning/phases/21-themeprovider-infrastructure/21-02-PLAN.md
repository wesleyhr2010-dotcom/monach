Wait, let me reconsider the anti-flash approach. Looking at the original ROADMAP success criteria:
- "Recarregar /app com o OS em dark mode e sem preferência salva: a PWA carrega diretamente no tema escuro, sem flash do fundo claro"

The flash happens because the HTML is rendered by the server (or statically) before JavaScript runs. The server doesn't know the user's OS preference. So the initial HTML has a light background, then when JS runs it switches to dark.

For the PWA (/app), pages are dynamic (`force-dynamic`) so they're server-rendered per request. The server still can't access `prefers-color-scheme`. So the anti-flash script must run in the browser immediately on page load.

The most robust anti-flash pattern is:
1. Server renders `<html>` or `<body>` with a default theme (usually light)
2. An inline script in the `<head>` or at the top of `<body>` reads localStorage + OS preference and sets the theme class/attribute BEFORE the browser paints
3. This prevents the flash because the script runs synchronously during HTML parsing

For our case, since we're using `data-theme` on `.app-shell` and `.admin-layout`, and those elements are in the React tree (not in the raw HTML), we need to ensure:
- The inline script runs as soon as possible
- If the element doesn't exist yet (because it's client-rendered), the script should use a MutationObserver or just accept that there might be a brief flash

Actually, a better approach: put the data-theme on `<body>` or `<html>` instead of on the shell div. But that would require changing how CSS selectors work.

Looking at globals.css:
```css
.app-shell[data-theme="dark"] { ... }
.admin-layout[data-theme="dark"] { ... }
```

The tokens are scoped to these classes. If we put data-theme on `<html>` instead, we'd need to change all the CSS selectors.

The pragmatic approach: the script targets the shell element. If it doesn't exist yet, it retries with a very short timeout (but this still might flash). Alternatively, we can put the data-theme attribute on the server-rendered element directly.

For /app: the AppShell is a Client Component rendered inside a Server Component layout. The server layout can render the `<div className="app-shell">` wrapper, and the client AppShell can render its children inside it. But that would require restructuring.

Actually, the simplest anti-flash that works:
- The server layout renders a `<script>` that sets `data-theme` on the first element with class `app-shell` or `admin-layout` it finds
- If not found immediately, it sets up a MutationObserver to watch for the element and set the attribute as soon as it appears
- The MutationObserver disconnects after finding the element

Let me update the approach in the plan. The inline script should be robust:

```javascript
(function() {
  var surface = "app"; // or "admin"
  var key = surface === "app" ? "monarca-app-theme" : "monarca-admin-theme";
  var className = surface === "app" ? "app-shell" : "admin-layout";
  var stored = localStorage.getItem(key);
  var theme = stored || "system";
  var resolved = theme === "system"
    ? (window.matchMedia("(prefers-color-scheme: dark)").matches ? "dark" : "light")
    : theme;
  
  function setTheme() {
    var el = document.querySelector("." + className);
    if (el) {
      el.setAttribute("data-theme", resolved);
      return true;
    }
    return false;
  }
  
  if (!setTheme()) {
    var observer = new MutationObserver(function() {
      if (setTheme()) {
        observer.disconnect();
      }
    });
    observer.observe(document.documentElement, { childList: true, subtree: true });
    // Safety timeout
    setTimeout(function() { observer.disconnect(); }, 1000);
  }
})();
```
