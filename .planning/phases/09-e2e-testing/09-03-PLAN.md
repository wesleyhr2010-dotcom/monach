## Password Recovery Flow (from SPEC_RECUPERAR_CONTRASENA.md)

1. User clicks "Esqueci minha senha" on /app/login
2. Enters email → system sends reset email via Supabase Auth + Brevo SMTP
3. Email contains link to /app/login/reset-password?token={token}
4. User enters new password → system updates via Supabase Auth
5. User can log in with new password

Route: `/app/login/reset-password`

<task type="auto">
  <name>Task 2: CI/CD Integration for E2E</name>
  <files>
    .github/workflows/ci-e2e.yml

  <action>
    1. Create `.github/workflows/ci-e2e.yml`:
       - Trigger: pull_request to main/develop, manual workflow_dispatch
       - Runs on: ubuntu-latest
       - Steps:
         a. Checkout code
         b. Setup Node.js 20 with npm cache
         c. Install dependencies: `npm ci`
         d. Install Playwright browsers: `npx playwright install chromium` (only chromium for speed)
         e. Setup test database:
            - Option A: If using local Supabase in CI, run `npx supabase start` (requires Docker, may be slow)
            - Option B: If using a dedicated test DB on Supabase, set DATABASE_URL from secrets
            - **Recommended:** Use the same DATABASE_URL secret but point to a test project/schema. Document this in workflow comments.
         f. Push Prisma schema: `npx prisma db push` (to ensure test DB has latest schema)
         g. Run E2E tests: `npm run test:e2e`
         h. Upload Playwright report on failure: use `actions/upload-artifact@v4` to upload `playwright-report/` and `test-results/` directories
       - Environment variables from secrets:
         - DATABASE_URL (test database)
         - DIRECT_URL (if different from DATABASE_URL)
         - NEXT_PUBLIC_SUPABASE_URL
         - NEXT_PUBLIC_SUPABASE_ANON_KEY
         - SUPABASE_SERVICE_ROLE_KEY (for seed helpers)
         - All R2_* values (can be dummy values if tests don't hit R2)
         - BREVO_API_KEY (can be dummy if tests don't send real emails — use generateRecoveryLink instead)
         - ONESIGNAL_APP_ID, ONESIGNAL_REST_API_KEY (can be dummy)
       - The workflow should NOT block on lint/typecheck (those are in ci-quality-gate.yml)
       - Set timeout to 10 minutes (E2E should complete in < 5 min)

    2. Update `.github/workflows/ci-quality-gate.yml`:
       - Add a comment or note that E2E tests run in a separate workflow (`ci-e2e.yml`)
       - Optionally, add a workflow_call or needs dependency if you want E2E to run after quality gate passes
       - **Decision:** Keep them separate. Quality gate (fast: lint + unit tests) runs first. E2E (slower) runs in parallel or after. For v1.2, parallel is fine — E2E has its own trigger conditions.
       - If the team wants E2E to block PR merge: ensure ci-e2e.yml is marked as a required check in branch protection (this is a GitHub setting, not a file change — document it in the E2E docs).

    3. Consider adding `continue-on-error: false` for the E2E step (default, but explicit is clearer). A failing E2E should block the PR.
  </action>

## STRIDE Threat Register

|-----------|----------|-----------|-------------|-----------------|
| T-09-07 | Information Disclosure | CI secrets exposed in logs | mitigate | Use GitHub secrets (`${{ secrets.XXX }}`); never echo DATABASE_URL or SUPABASE_SERVICE_ROLE_KEY |
| T-09-08 | Information Disclosure | Playwright artifacts contain PII screenshots | accept | Test data uses fake PII; artifacts only retained for 30 days (GitHub default) |
| T-09-09 | Denial of Service | E2E CI runs on every PR → cost/compute | accept | Workflow limited to PRs (not every push); only Chromium installed; 10-min timeout |
